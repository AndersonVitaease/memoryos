# ADR-005 — Connector Registry: Consolidação
**ADR-ID:** ADR-005
**Título:** Connector Registry: Declaração de Canonical e Estratégia de Consolidação
**Data:** 2026-07-11
**Status:** Proposed
**DAP de origem:** DAP-05
**Sprint:** SPR-ADR-01

---

## 1. Contexto

### Por que a decisão existe

Existem pelo menos 5 implementações de Connector Registry no codebase, sem declaração de qual é o canonical. O produto usa `src/lib/connectors/registry.js` via `getConnectorsForService()` em `capabilityOrchestrator.js`. Os outros 4 existem como módulos independentes sem integração ativa ao produto.

EF-16 (Connector Registry v1.0) planeja consolidação, mas não tem cronograma definido nem implementação iniciada. Enquanto o canonical não for declarado, qualquer novo desenvolvimento de connector pode usar qualquer uma das 5 implementações, aumentando a fragmentação.

**Nota crítica:** A auditoria ARCHITECTURE-VALIDATION-REPORT §2.12 identificou que Capability Registry e Connector Registry são conceitos distintos sendo tratados conjuntamente. Esta ADR trata exclusivamente do Connector Registry.

### Componentes afetados

- `src/lib/connectors/registry.js` — usado pelo produto (canonical de facto)
- `src/lib/connector-registry/` — 11 arquivos JavaScript (não usado pelo produto)
- `src/lib/connector-runtime/ConnectorRegistry.ts` — TypeScript, embutido no Connector Runtime
- `src/lib/enterprise-integration/connectorRegistry.js` — JavaScript, não usado pelo produto
- `src/lib/connector-sdk/` — 12 arquivos JavaScript (SDK layer)
- `src/lib/reasoning/capabilityOrchestrator.js` — usa `connectors/registry.js`
- Connector Runtime — depende de Connector Registry para lookup de conectores

### Evidências do código

- `src/lib/reasoning/capabilityOrchestrator.js` — import de `@/lib/connectors/registry`
- `src/lib/connectors/registry.js` — `getConnectorsForService()` — usado no produto
- `src/lib/connector-registry/connectorRegistry.js` — implementação separada, 11 arquivos
- `src/lib/connector-runtime/ConnectorRegistry.ts` — terceira implementação
- `src/lib/enterprise-integration/connectorRegistry.js` — quarta implementação
- AUDIT-Sprint0 — quadruplicação confirmada (5ª instância identificada no VALIDATION-REPORT)
- BLOQ-04 no ARCHITECTURE-FREEZE-CHECKLIST — bloqueia congelamento
- RA-01 no ARCHITECTURE-RISK-REGISTER — risco alto

---

## 2. Problema

### Conflito existente

Cinco implementações sem canonical declarado. O produto usa `connectors/registry.js` mas não está documentado como oficial. `connector-runtime/ConnectorRegistry.ts` é TypeScript e usa API diferente. `connector-registry/` tem 11 arquivos com search, lookup, compatibility, filters, catalog, statistics — funcionalidades não presentes nas outras implementações.

A ausência de canonical cria risco operacional: qualquer sprint futura de connector pode usar qualquer implementação, e sem um ponto de consolidação, o problema cresce.

### Por que impede o congelamento

BLOQ-04: Connector Registry canonical não declarado. O congelamento exige que registries tenham source-of-truth único. EF-16 não tem implementação — sem canonical temporário declarado, o congelamento não pode ocorrer.

## 3. Alternativas

### Alternativa A — Declarar `connectors/registry.js` como canonical temporário

**Como funciona:** `src/lib/connectors/registry.js` é declarado official canonical do Connector Registry até EF-16. Os outros 4 são congelados (não recebem novos desenvolvimentos). EF-16 consolidará tudo quando implementado.

**Vantagens:**
- Zero esforço de implementação
- Não quebra o produto (já usa este arquivo)
- Resolve BLOQ-04 com ação editorial (documentação)
- Congela crescimento das outras 4 implementações

**Desvantagens:**
- `connectors/registry.js` é JavaScript sem Types EF
- Não tem a estrutura formal de EF (sem health, metrics, statistics)
- Canonical temporário cria dívida técnica até EF-16

**Impacto:** Zero no produto. Editorial apenas.

**Risco:** Baixo — produto continua funcionando exatamente como está.

**Esforço estimado:** < 1 hora (documentação + comentário no arquivo).

---

### Alternativa B — Declarar `connector-registry/` como canonical e migrar o produto

**Como funciona:** `src/lib/connector-registry/` (11 arquivos) é declarado canonical. `capabilityOrchestrator.js` é atualizado para usar `connector-registry/connectorRegistry.js` em vez de `connectors/registry.js`.

**Vantagens:**
- `connector-registry/` tem funcionalidades mais ricas (search, lookup, filters, statistics)
- Mais próximo do que EF-16 precisaria formalmente

**Desvantagens:**
- Requer migração em `capabilityOrchestrator.js` — risco de regressão
- `connector-registry/` é JavaScript sem verificação de que cobre exatamente `getConnectorsForService()`
- Adiciona complexidade antes de validação

**Impacto:** Médio — altera import no produto.

**Risco:** Médio — mudança de comportamento potencial se APIs diferirem.

**Esforço estimado:** 0.5 sprint (análise + migração + testes).

---

### Alternativa C — Implementar EF-16 imediatamente consolidando tudo

**Como funciona:** Implementar Connector Registry v1.0 (EF-16) agora, unificando as 5 implementações. Certificar com 28 cenários. Migrar produto para EF-16.

**Vantagens:**
- Solução definitiva
- Sem dívida técnica residual
- Connector Runtime pode ser desenvolvido contra EF-16 canonical

**Desvantagens:**
- Sprint completa antes de qualquer outra integração
- Analisa e unifica 5 implementações com APIs potencialmente incompatíveis
- Bloqueia INT-04+ até EF-16 estar pronto

**Impacto:** Alto — sprint adicional bloqueante.

**Risco:** Alto — complexidade de unificação de 5 implementações.

**Esforço estimado:** 2-3 sprints (análise + design + implementação + certificação).

---

### Alternativa D — Separar decisão: canonical temporário agora, EF-16 depois

**Como funciona:** Fase 1 (imediata): Alternativa A — declarar `connectors/registry.js` como canonical temporário (editorial). Fase 2 (futuro): EF-16 implementado quando roadmap permitir.

**Vantagens:**
- Resolve BLOQ-04 agora com zero esforço
- EF-16 não bloqueia o restante do roadmap
- Connector Runtime pode ser desenvolvido contra o canonical temporário declarado

**Desvantagens:**
- Dívida técnica por período maior
- Connector Runtime terá que migrar de novo quando EF-16 vier

**Impacto:** Mínimo agora; médio quando EF-16 chegar.

**Risco:** Baixo agora; gerenciável no futuro.

**Esforço estimado:** < 1 hora agora; 2 sprints no futuro.

## 7. Recomendação Técnica

**Recomendação: Alternativa D (canonical temporário agora, EF-16 depois)**

Fundamentação:

1. Resolve BLOQ-04 com ação editorial mínima (< 1 hora)
2. Não introduz risco de regressão no produto (Alt. B) nem bloqueia roadmap (Alt. C)
3. `connectors/registry.js` já é o canonical de facto — a declaração é apenas formalização do estado atual
4. EF-16 pode ser planejado sem urgência, não bloqueando INT-02 a INT-06

**Ação mínima para desbloquear BLOQ-04:**
1. Adicionar comentário em `connectors/registry.js`: `// CANONICAL TEMPORÁRIO — EF-16 substituirá`
2. Adicionar comentário nos outros 4: `// CONGELADO — não adicionar funcionalidades; canonical em connectors/registry.js`
3. Registrar decisão em ARCHITECTURE-DECISION-LOG após aprovação humana

*Esta recomendação não constitui aprovação. A decisão final deve ser tomada por humano.*
