# ADR-014 — Microsoft Graph Connector: Provider Router + Multi-Account

**Status:** Accepted
**RFC Origem:** RFC-007
**Emenda a:** ADR-013 (circunscrita à camada de Provider; o restante de ADR-013 permanece válido)
**Prioridade:** ALTA
**Sprints afetadas:** MS-PR-01 a MS-PR-04 (MS-EXP-05 — MicrosoftWatchProvider — desvinculado, permanece opcional)
**Data:** 2026-08-04
**Autor:** MemoryOS Engineering

---

## Contexto

O `MicrosoftGraphConnector` atual (RFC-006 / ADR-013, concluídos) expõe 32 operations via 11 Capability Executors isolados, com shell fino que decide "como" executar: pega token (Flow 1 — OAuth próprio) e delega ao `MicrosoftCapabilityRegistry`.

O ADR-013 **rejeitou** explicitamente a alternativa C (Provider Registry estilo WhatsApp) com a justificativa: *"o Microsoft Graph é uma única API oficial — não há provedores concorrentes a abstrair. Criar `MicrosoftProviderRegistry` com um único `GraphProvider` seria indireção sem benefício."*

**O contexto evoluiu desde então.** Em 2026-08-04, ao configurar o redirect URI do Microsoft App Registration, descobriu-se que existem **dois fluxos OAuth viáveis e concorrentes** para acessar o mesmo Microsoft Graph:

1. **Flow 1 — OAuth próprio** (já existe): `microsoftOAuthInit`/`Exchange` + entidade `MicrosoftOAuthToken`, redirect URI na rota do app, refresh no backend, multi-conta via `workspaceId`.
2. **Flow 2 — Base44 App-User Connector** (descoberto): `register_workspace_connector` + `base44.connectors.connectAppUser(connectorId)`, redirect URI gerenciada pelo Base44 (única por app, ambientes Live + Preview + Custom domain), gestão de token delegada à plataforma.

Sem um Provider Router, escolher entre os dois fluxos exige um `if` espalhado pelo código — exatamente o padrão rejeitado pelo projeto. Além disso, o usuário pediu **multi-conta simultânea** (já existente no Google Workspace) como requisito de primeira classe.

---

## Decisao

Adotar uma camada de **Provider Router** entre o shell do conector e a execução, **workspaceId-aware** (multi-conta de primeira classe):

1. O `MicrosoftGraphConnector` torna-se um shell que **delega a decisão** ao `MicrosoftProviderRegistry`.
2. Cada provider implementa a interface `MicrosoftProvider` (espelha `WhatsAppProvider`, mas `workspaceId`-aware).
3. O router pergunta "quem consegue executar `operation` para a conta `workspaceId`?" e devolve o primeiro provider disponível.
4. O `MicrosoftCapabilityRegistry` e os 11 executors (ADR-013) **permanecem intactos** — viram internos do `OfficialGraphProvider`.

### Lineup de providers

| Provider | Status | Auth |
|---|---|---|
| `OfficialGraphProvider` | Re-homed do shell atual | Flow 1 (OAuth próprio, multi-conta via `workspaceId`) |
| `Base44OutlookProvider` | Novo (Fase 4, opcional) | Flow 2 (App-User Connector) |
| `McpMicrosoftProvider` | Stub interface-conforme | Servidor MCP (Softeria descartado) |
| `RestSdkProvider` | Stub interface-conforme | Graph JS SDK / REST alternativo |

---

## Emenda a ADR-013 (circunscrita)

O ADR-013 rejeitou a alternativa C com base em "indireção sem benefício". Esta ADR **emenda** essa rejeição, sem revogar o restante do ADR-013:

- **O que permanece válido em ADR-013:** o padrão Capability Executors (shell fino + 11 executors isolados), o `MicrosoftCapabilityRegistry`, o `MicrosoftGraphHelper`, os escopos OAuth incrementais.
- **O que é emendado:** a rejeição da camada de Provider. A justificativa original era correta quando escrita (Graph como API única). O contexto evoluiu: hoje existem **dois fluxos OAuth viáveis** para a mesma API, e a indireção agora traz valor (resolve o dilema OAuth sem `if`s espalhados + suporta multi-conta de primeira classe).
- **Escopo da emenda:** exclusivamente a introdução da camada de Provider Router. Os 11 executors não são tocados.

A diferença sutil vs. WhatsApp: no WhatsApp, o Provider abstrai **qual backend** chamar (APIs diferentes). No Microsoft, o Provider abstrai **qual credencial** usar para chamar a **mesma** API (Graph). Os providers não são APIs concorrentes; são **estratégias de acesso**.

## Alternativas Consideradas

### Alternativa A — `if` espalhado entre os dois fluxos OAuth (rejeitada)
- **Pro:** zero arquitetura nova.
- **Contra:** lógica de "qual fluxo usar" espalhada pelo shell e pelos executors; multi-conta vira `if` adicional; mudar de fluxo exige refator em vários pontos. Repete o padrão rejeitado pelo projeto.

### Alternativa B — Provider Router workspaceId-aware (ACEITA)
- **Pro:** ambos os fluxos coexistem atrás da mesma interface; multi-conta resolvida no lookup; novo provider = 1 arquivo + 1 linha no registry; troca de fluxo preferido = 1 linha.
- **Contra:** mais arquivos agora (tipos + registry + 4 providers).
- **Decisão:** a indireção agora tem valor real (dois fluxos OAuth viáveis + multi-conta), justificando a camada.

### Alternativa C — Migrar tudo para o Base44 App-User Connector e descartar o OAuth próprio (rejeitada)
- **Pro:** gestão de token 100% delegada à plataforma.
- **Contra:** perde-se cobertura das 32 operations (o connector `outlook` nativo cobre subset); perde-se controle do refresh/multi-conta; dependência total da plataforma para qualquer ajuste.

---

## Justificativa

A descoberta do segundo fluxo OAuth viável (App-User Connector) mudou o trade-off que motivou a rejeição em ADR-013. Agora há genuínamente "provedores concorrentes" — não de API, mas de **estratégia de acesso**. Sem abstração, escolher entre eles vira `if` espalhado.

O multi-conta elevado a requisito de primeira classe (espelhando o Google Workspace, já vivo em produção) exige que o `workspaceId` flua do shell até o token — o que é natural na arquitetura de Provider, mas seria um retrofit desconfortável no shell monolítico.

A arquitetura espelha o padrão **vivo e em produção** do WhatsApp (`WhatsAppProviderRegistry`), adicionando `workspaceId`-awareness — consistência com a decisão arquitetural do projeto de estruturar conectores em camadas explícitas (Capability, Provider, Event, Observation, Watch).

---

## Consequencias

- **Positivas:**
  - Dilema OAuth (Flow 1 vs Flow 2) resolvido sem `if`s; router escolhe por disponibilidade/preferência.
  - Multi-conta de primeira classe: `workspaceId` flui do shell ao token; UI de switcher espelha Google.
  - Novo provider = 1 arquivo + 1 linha no registry; shell, planner e capability registry intocados.
  - Troca de provider preferido ou depreciação sem migração de usuários.
  - Slots reservados (MCP, REST/SDK) prontos para o futuro sem código morto.

- **Negativas:**
  - Mais arquivos no repositório (tipos + registry + 4 providers).
  - Refator da Fase 2 para re-homed do shell atual no `OfficialGraphProvider` (comportamento idêntico, teste de paridade obrigatório).

- **Neutras:**
  - ADR-013 é emendado, não revogado; os 11 executors permanecem intactos.
  - O Softeria MCP permanece descartado (dead end); o slot MCP é stub interface-conforme, não implementação ativa.

## Resumo das Decisoes

1. **Camada de Provider Router:** introduzida entre o shell e a execução; o shell deixa de decidir "como".
2. **Emenda circunscrita a ADR-013:** apenas a camada de Provider; Capability Executors e registry de executors permanecem.
3. **Espelho do WhatsApp:** `MicrosoftProviderRegistry` singleton HMR-safe, `MicrosoftProvider` interface.
4. **Multi-conta de primeira classe:** `workspaceId` flui do shell ao token; UI switcher espelha Google.
5. **Lineup realista:** OfficialGraph (ativo), Base44Outlook (opcional, futuro), MCP + REST/SDK (stubs).
6. **Softeria permanece descartado:** slot MCP é stub interface-conforme, não implementação.
7. **Sem árvore paralela:** `microsoft-providers/` fica dentro de `connectors/`, irmão de `microsoft/`.
8. **Aditivo e reversível:** Fases 1-3 não mudam comportamento; Fase 4 é opcional.

---

## Fases de Implementacao

- **Fase 0 — Documentação (este ADR + RFC-007):** só documento, zero código.
- **Fase 1 — Tipos + Registry:** `MicrosoftProviderTypes.ts` + `MicrosoftProviderRegistry.ts`, 0 providers ativos.
- **Fase 2 — OfficialGraphProvider:** re-home do shell atual; paridade das 32 operations.
- **Fase 3 — Stubs MCP + REST/SDK:** interface-conformes, `isAvailable()=false`.
- **Fase 4 — Base44OutlookProvider (opcional):** segundo provider de verdade; resolve o dilema OAuth.

Cada fase é aditiva e reversível.
