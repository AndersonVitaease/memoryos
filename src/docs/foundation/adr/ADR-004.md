# ADR-004 — Capability Runtime: Certificação e Consolidação
**ADR-ID:** ADR-004
**Título:** Capability Runtime (EF-15): Auditoria de Certificação e Consolidação do Registry
**Data:** 2026-07-11
**Status:** Proposed
**DAP de origem:** DAP-04
**Sprint:** SPR-ADR-01

---

## 1. Contexto

### Por que a decisão existe

Capability Runtime existe em `src/lib/capability-runtime/` com estrutura completa (Types, Executor, Loader, Registry próprio, Capabilities implementadas). Contudo, a auditoria automática retornou `testCount=0`, o que normalmente indicaria ausência de certificação EF.

Simultaneamente, existe uma triplicação de Capability Registry: o oficial (EF-14 em `src/lib/capability-registry/`), o embutido no Capability Runtime (`src/lib/capability-runtime/CapabilityRegistry.ts`), e o legado JavaScript (`src/lib/capabilities/registry/`). O Capability Runtime usa seu próprio Registry interno em vez do EF-14 oficial — violação arquitetural.

INT-04 (integração de Capability Runtime no produto como substituto de `CapabilityOrchestrator`) depende da resolução deste cenário.

### Componentes afetados

- `src/lib/capability-runtime/` — módulo a auditar/certificar
- `src/lib/capability-runtime/CapabilityRegistry.ts` — duplicata a deprecar
- `src/lib/capability-registry/` (EF-14) — registry oficial, 28 cenários
- `src/lib/capabilities/registry/` — legado JavaScript a deprecar
- `src/lib/reasoning/capabilityOrchestrator.js` — componente a ser substituído no produto
- Decision Engine (EF-06) — produz input para Capability Runtime

### Evidências do código

- `src/lib/capability-runtime/capabilityRuntimeTests.ts` — arquivo existe; testCount=0 no auditor automático
- `src/lib/capability-runtime/CapabilityRegistry.ts` — duplicata interna
- `src/lib/capability-registry/CapabilityRegistry.ts` (EF-14) — oficial, 28 cenários
- `src/lib/capabilities/registry/` — terceira implementação (JavaScript, legado)
- AUDIT-Sprint0 §5.1 — triplicação confirmada
- ARCHITECTURE-VALIDATION-REPORT §2.10 — status ❌ Incompatível (triplicação)
- ARCHITECTURE-VALIDATION-REPORT §2.11 — status 🟡 (testCount=0)
- BLOQ-03 no ARCHITECTURE-FREEZE-CHECKLIST — bloqueia congelamento

## 2. Problema

### Conflito existente

**Problema 1 — Certificação incerta:** `testCount=0` pode ser:
- Falso negativo: o arquivo de testes usa estrutura diferente da regex do auditor
- Verdadeiro: não existem cenários de aceitação formais EF

Sem resolver esta ambiguidade, não é possível determinar se EF-15 está pronto para INT-04 ou se precisa de sprint de implementação.

**Problema 2 — Violação arquitetural:** Capability Runtime usa `CapabilityRegistry` próprio em vez de EF-14. Isso viola o princípio de registry central único. Se Capability Runtime for integrado no produto sem corrigir esta violação, haverá dois registries ativos simultaneamente.

### Por que impede o congelamento

BLOQ-03: Capability Registry canonical não declarado — 3 implementações. O congelamento exige source-of-truth único. Adicionalmente, se testCount=0 é verdadeiro, EF-15 precisaria de sprint de implementação antes de INT-04.

## 3. Alternativas

### Alternativa A — Auditar manualmente capabilityRuntimeTests.ts, depois decidir

**Como funciona:** Ler `capabilityRuntimeTests.ts` e contar cenários manualmente. Se >= 28 no padrão EF: certificar e prosseguir para Alternativa A2. Se < 28: implementar cenários faltantes.

**Alternativa A1 (se >= 28 cenários):**
- Corrigir Capability Runtime para usar EF-14 em vez de seu Registry interno
- Deprecar `capability-runtime/CapabilityRegistry.ts`
- Deprecar `capabilities/registry/` legado
- INT-04 pode prosseguir

**Alternativa A2 (se < 28 cenários):**
- Completar cenários até 28
- Depois: A1

**Vantagens:**
- Aproveita trabalho existente
- Menor esforço se testCount=0 é falso negativo
- Decisão baseada em evidência real (leitura do arquivo)

**Desvantagens:**
- Requer ação manual de leitura antes de qualquer outra alternativa
- Pode revelar que todo o Capability Runtime precisa ser reescrito

**Impacto:** Variável — depende do resultado da leitura.

**Risco:** Médio — incerteza até a leitura.

**Esforço estimado:** Auditoria manual: horas. Correção de Registry: < 1 sprint. Implementação de cenários se necessário: 1 sprint.

---

### Alternativa B — Implementar EF-15 do zero seguindo padrão EF

**Como funciona:** Nova implementação de Capability Runtime ignorando o existente. 28 cenários formais. Usa EF-14 desde o início.

**Vantagens:**
- Certeza de certificação
- Padrão uniforme com todos os outros módulos
- Sem herança de problemas da implementação anterior

**Desvantagens:**
- Descarta trabalho existente (Executor, Loader, Capabilities implementadas)
- Sprint completa: mais longa que corrigir o existente
- Capabilities implementadas (Base44InfoCapability, GitHubReadCapability) precisariam ser reimplementadas

**Impacto:** Maior esforço, resultado mais limpo.

**Risco:** Baixo — resultado final.

**Esforço estimado:** 2-3 sprints (design + implementação + certificação + consolidação de registry).

---

### Alternativa C — Completar EF-15 adicionando o que falta ao existente

**Como funciona:** Manter a implementação atual de Capability Runtime. Adicionar cenários EF formais até 28. Substituir `CapabilityRegistry` interno pelo EF-14. Deprecar legado.

**Vantagens:**
- Preserva Executor, Loader, Capabilities implementadas (Base44, GitHub)
- Adiciona apenas o necessário
- Resultado final equivalente à Alternativa A (se testCount=0 é verdadeiro)

**Desvantagens:**
- Se implementação existente tem problemas arquiteturais, serão herdados
- Requer leitura profunda do código para entender o que pode ser reaproveitado

**Impacto:** Médio — modificação incremental.

**Risco:** Médio — depende da qualidade do código existente.

**Esforço estimado:** 1-2 sprints.

## 7. Recomendação Técnica

**Recomendação: Alternativa A (Auditar manualmente antes de qualquer outra ação)**

Fundamentação:

1. Não é possível recomendar B ou C sem saber o estado real de `capabilityRuntimeTests.ts`
2. A leitura do arquivo é obrigatória — é a menor ação possível com maior informação retornada
3. Se testCount=0 for falso negativo (cenários existem mas em estrutura diferente), o esforço é mínimo (apenas substituir o Registry interno)
4. Se testCount=0 for verdadeiro, o esforço é conhecido e a Alternativa C é preferível à B (preserva Capabilities implementadas)

**Ação mínima para desbloquear BLOQ-03:**
Independente do resultado da auditoria manual:
1. Declarar `src/lib/capability-registry/` (EF-14) como canonical oficial imediatamente
2. Marcar `src/lib/capability-runtime/CapabilityRegistry.ts` como `@deprecated`
3. Marcar `src/lib/capabilities/registry/` como `@deprecated`

Esta ação resolve BLOQ-03 sem implementar código.

*Esta recomendação não constitui aprovação. A decisão final deve ser tomada por humano.*
