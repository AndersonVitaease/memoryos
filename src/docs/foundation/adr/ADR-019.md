# ADR-019 — Web Connector: Autenticação por Sessão (sem cofre de credenciais)

**Status:** Accepted
**Data:** 2026-08-09
**RFCs relacionadas:** RFC-012, RFC-013, RFC-014 (substituem o modelo de dados de `RFC-WEB-CONNECTOR-HYBRID.md`)
**Autores:** Anderson (arquitetura corrigida), Claude (documentação, correção de erro de processo)

---

## Contexto

O documento `RFC-WEB-CONNECTOR-HYBRID.md` (raiz do repo, DRAFT, autor Anderson, 2026-08-09) propôs originalmente um modelo de **cofre de credenciais**: entidade `UserCredential` armazenando `encryptedEmail` e `encryptedPassword` (AES-256-GCM) por usuário/site, com o MemoryOS fazendo login automatizado em nome do usuário usando essas credenciais.

### Nota de correção de processo

Numa sessão de planejamento subsequente, esse modelo foi levado adiante numa proposta de implementação **sem revalidar se era a melhor abordagem** — e, mais grave, uma implementação inteira baseada nele chegou a ser construída num ambiente de sandbox isolado da conversa, nunca sincronizado com este app Base44, consumindo tempo do usuário sem entregar nada real. Esse trabalho foi descartado; nenhum arquivo deste app foi afetado por ele. Esta ADR existe para registrar a correção de rumo formalmente, como qualquer outra decisão de arquitetura do projeto.

Anderson então forneceu a arquitetura correta: o MemoryOS **nunca deve receber ou armazenar a senha do usuário** para sistemas externos. A autenticação deve acontecer diretamente no site, na sessão própria do usuário — o Web Connector reaproveita essa sessão já autorizada (via cookies capturados) em vez de repetir login com credenciais guardadas.

---

## Decisão 1 — Nunca armazenar senha de terceiros, em nenhuma forma

**Decisão:** O Web Connector não tem, em nenhuma fase, um campo de senha. Nem em texto puro, nem criptografado.

**Alternativas consideradas:**
- A) Cofre de credenciais criptografado (`UserCredential`, AES-256-GCM) — **rejeitado**. Custódia de senha de terceiros cria superfície de risco (vazamento, LGPD/GDPR, responsabilidade legal) que é evitável quando existe alternativa técnica viável.
- B) OAuth quando o site suporta — **aceito como complementar**, não como via principal. Nem todo sistema-alvo (ex: intranets, ERPs legados, Wooba) expõe OAuth.
- C) Captura de sessão (cookies) após login direto do usuário no site — **aceito como via principal**.

**Consequência:** A entidade `UserCredential` descrita na RFC original nunca é criada. Toda menção a "credential vault" em planejamentos anteriores está superseded por esta ADR.

---

## Decisão 2 — `WebSession` substitui `UserCredential` como entidade central

**Decisão:** Nova entidade `WebSession`: site, cookies capturados, `browser_context_id`, TTL, status. Sem campo de senha, sem campo de email do site (apenas o necessário para identificar a sessão).

**Consequência:** Ver RFC-012 para o schema completo e o fluxo de captura.

---

## Decisão 3 — Duas vias de captura de sessão, não-bloqueantes entre si

**Decisão:**
- **Via principal (Frente A / RFC-012):** MemoryOS abre a URL num contexto Playwright dedicado, exibido ao usuário; o usuário loga manualmente; cookies são capturados ao final do login.
- **Via complementar (Frente D, adiada):** Extensão Chrome captura a sessão de uma aba onde o usuário já está logado. Fica para depois de A/B/C validados com um site real — não é pré-requisito.

**Razão da ordem:** a via Playwright é mais mecânica e testável isoladamente; a extensão é uma superfície de produto nova (Manifest V3) que não deve bloquear a validação do núcleo.

## Riscos identificados

| Risco | Mitigação |
|---|---|
| Sessão expira (TTL do site é mais curto que o esperado) | `WebSession.status` transiciona para `expired`; usuário é solicitado a reautenticar manualmente, sem fricção de reconfigurar o connector |
| Exibir o browser ao usuário durante login aumenta custo de UX | Modo `headed` apenas durante a etapa de login; volta para `headless` depois que os cookies são capturados |
| Confusão entre este RFC-001 (raiz, legado) e o RFC-001.md canônico já existente em `src/docs/foundation/rfc/` | Ver nota de numeração abaixo — o documento raiz nunca foi movido para a árvore canônica e usava numeração própria colidente |

## Nota de numeração

O arquivo raiz `RFC-WEB-CONNECTOR-HYBRID.md` se autodenomina "RFC-001" internamente, mas nunca esteve na árvore canônica `src/docs/foundation/rfc/`, que já tem um `RFC-001.md` real e não relacionado. Os novos documentos desta iniciativa usam a numeração canônica correta (RFC-012 a RFC-014, sequência real do diretório) para evitar repetir esse tipo de inconsistência — o mesmo problema já registrado para a árvore `00-official-library/` vs `foundation/`.

## Não-decisões (fora de escopo desta ADR)

- SSO corporativo / credenciais compartilhadas por empresa — considerar apenas após o modelo de sessão individual estar validado.
- Extensão Chrome (Frente D) — RFC futuro, após RFC-012/013/014 validados com pelo menos 1 site real.

## Adendo (2026-08-09) — Bootstrap de login vs. execução de capabilities

Esclarecimento de Anderson durante o Sprint 1: a execução recorrente de ações (capabilities — RFC-013/014) é **100% headless, orientada por operação estruturada**, sem qualquer necessidade de o usuário ver uma tela. Isso nunca esteve em risco.

A questão real era só sobre o **bootstrap único de login** (primeira captura de sessão por site/usuário, RFC-012): a instância Playwright da VPS roda `--headless` (sem tela física), então "sessão visível" não pode significar uma janela real. Decisão para o MVP:

- O bootstrap usa **snapshot/screenshot exibido na UI do MemoryOS + campos de formulário**, que são repassados ao Playwright headless via `browser_type`/`browser_click` (mesma mecânica já usada no login determinístico do `bugHunterRun`).
- **Consequência explícita:** durante esse passo único, a senha **transita** pela função backend (`webConnectorConnect`) a caminho do Playwright — nunca é persistida em nenhuma entidade, nunca vai para log (`console.log`/`history.push` nunca deve incluir o valor de senha), e é descartada da memória do processo assim que o `browser_type` retorna. Apenas os **cookies resultantes** viram `WebSession`.
- Isso é mais fraco que "o MemoryOS nunca recebe a senha" no sentido mais estrito, mas segue muito mais forte que o cofre de credenciais original (Seção 2.2 do RFC-001 legado): nada é armazenado, nada é reutilizável após o bootstrap.
- A via que cumpriria "senha nunca toca o MemoryOS" de forma estrita mesmo no bootstrap é a extensão Chrome (Frente D) — permanece como evolução futura, não bloqueia o MVP.
