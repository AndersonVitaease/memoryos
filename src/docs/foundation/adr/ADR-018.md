# ADR-018 — Flight Domain Provider Router (Travelport + Travellink)

**Status:** Accepted
**RFC Origem:** RFC-011
**Prioridade:** ALTA
**Sprints afetadas:** GDS-01 a GDS-08
**Data:** 2026-08-06
**Autor:** MemoryOS Engineering

---

## Contexto

O usuário obteve credenciais de trial da Travelport TripServices (GDS Galileo, JSON API/REST, OAuth2). Já existia base construída (sem credenciais) para a Travellink Web API (Wooba). O usuário confirmou que quer **ambos os conectores simultâneos**: Travelport para cobertura internacional (GDS), Travellink como consolidadora complementar/doméstica.

Isso é estruturalmente idêntico ao caso que originou o padrão de Provider no WhatsApp (ADR de origem): **duas APIs concorrentes de verdade** para o mesmo domínio de negócio (enviar mensagem / no caso atual, buscar-precificar-reservar-emitir passagem). Não é o caso do Microsoft Graph (ADR-014), onde os "providers" eram estratégias de acesso à mesma API — aqui Travelport e Travellink são sistemas diferentes, com protocolos diferentes (JSON/OAuth2 vs SOAP-like/RSA-PKCS1), catálogos de companhias aéreas diferentes.

## Decisão

Adotar uma camada de **Provider Router de domínio**, acima dos conectores individuais:

```
Planner → GoalCapabilityRegistry (flight.* → connector "flight-gds", INALTERADO por provider)
  → FlightConnector (shell fino, id "flight-gds")
    → FlightProviderRegistry (NOVO, singleton HMR-safe)
      → resolveProvider(operation, searchContext) → FlightProvider
        - TravelportProvider  (delega a TravelportConnector — Capability Executors ADR-013-like)
        - TravellinkProvider  (delega ao conector Travellink/Wooba já existente)
```

Os dois conectores concretos (`TravelportConnector`, conector Travellink) continuam existindo como Capability Layers independentes, cada um com seus próprios executors — o Provider Router não os substitui, apenas os expõe sob um Goal comum quando faz sentido agregar (`flight.search`) ou rotear por cobertura (`flight.book`/`flight.ticket`, que são específicos do PNR já aberto num provider específico — nesse caso o provider já está implícito pela cadeia anterior, não há ambiguidade a resolver).

### Diferença explícita vs ADR-014 (Microsoft)

| | Microsoft (ADR-014) | Flight (ADR-018) |
|---|---|---|
| O que os providers abstraem | Qual **credencial/fluxo OAuth** usar para a mesma API | Qual **API/sistema** usar para o mesmo domínio de negócio |
| APIs concorrentes de verdade? | Não — Graph é único | Sim — Travelport (GDS) e Travellink (consolidador) são sistemas distintos |
| Chave de seleção | `workspaceId` (conta do usuário) | Cobertura de carrier/rota (contexto da busca) |
| Padrão-mãe | Este é o segundo caso do padrão | Mesmo padrão do WhatsApp (ADR original) |

## Alternativas Consideradas

### A — Dois Goals totalmente separados (`travelport.air.search` vs `travellink.air.search`), sem unificação (rejeitada)
- **Pró:** zero indireção nova.
- **Contra:** viola o princípio arquitetural do projeto ("Planner nunca conhece conectores específicos, só Goals/Capabilities"). O usuário pediu explicitamente os dois simultâneos — sem unificação, cada mudança de cobertura exige mudar o Goal chamado, não só o roteamento interno.

### B — Provider Router de domínio, workspaceId-agnostic, chave por cobertura (ACEITA)
- **Pró:** Planner mantém-se desacoplado; unifica `flight.search` como ponto de agregação; troca/adição de provider = 1 arquivo + 1 registro, sem tocar o shell.
- **Contra:** mais uma camada de indireção para manter.
- **Decisão:** o caso genuíno de múltiplos backends concorrentes (idêntico ao WhatsApp) justifica a camada — ao contrário do Microsoft, aqui a indireção não é "emenda", é o caso canônico original do padrão.

### C — Fundir Travelport e Travellink num único conector monolítico (rejeitada)
- **Pró:** menos arquivos.
- **Contra:** APIs, protocolos de auth e modelos de dados divergem completamente (JSON/OAuth2 vs RSA-PKCS1); um switch único viraria um God Component rapidamente — exatamente o antipadrão já rejeitado em ADR-015 (Alternativa B) para o Dispatcher.

## Justificativa

O usuário definiu o requisito de primeira classe ("conectores simultâneos") antes mesmo de qualquer código existir — diferente do Microsoft, onde o Provider Router foi uma descoberta no meio do caminho. Adotar o padrão desde o início (RFC-011/GDS-08) evita reconstruir depois (como aconteceu com o Microsoft via ADR-014).

## Consequências

- `TravelportConnector` e o conector Travellink continuam evoluíveis de forma independente (cada um com seu próprio ritmo de sprints — Travelport tem credenciais agora, Travellink ainda não).
- `flight.ticket`/`flight.reissue` (irreversíveis) tornam-se o primeiro caso real de migração de caller para a cadeia ADR-015 (Execution Intelligence + Safety Gate) — ver RFC-011.
- Quando a Wooba enviar as credenciais da Travellink, a Fase GDS-08 já terá o slot pronto (`TravellinkProvider.ts`), sem necessidade de retrabalho arquitetural (mesmo padrão de "slot reservado" já usado nos stubs do WhatsApp e do Microsoft).
