# ADR-011 — Registro de Providers de IA (multi-provider, extensível por capacidade)

**Status:** Implemented
**Data:** 2026-07-30
**RFC:** N/A
**Autor:** Sessão de engenharia assistida (Claude) + Anderson Vitaease

---

## Contexto

O MemoryOS tinha um único caminho de geração de resposta (ETAPA 6 do `memoryReasoningPlanner.js`), sempre via `base44.integrations.Core.InvokeLLM` — sem alternativa, sem cache de prompt (não exposto pela API gerenciada do Base44), sem capacidade de rotear pedidos especializados (tradução, resumo, transcrição, geração de código) para modelos otimizados para cada tarefa.

Já existia um `OpenRouterConnector.ts` registrado no `ConnectorRegistry`, mas não usado no caminho de resposta principal. Também já existia — mas nunca testado — um sistema de roteamento por categoria (`categoryRouter.js`, `serviceDetector.js`) capaz de detectar pedidos como "traduza"/"resuma"/"transcreva" e rotear para o modelo OpenRouter apropriado.

## Decisão

1. Criado `src/lib/ai-provider-registry/` — registro genérico de providers de IA (`AIProviderTypes.ts`, `Base44LLMProvider.ts`, `OpenRouterLLMProvider.ts`, `AIProviderRegistry.ts`), seguindo o mesmo padrão arquitetural já usado por `ConnectorRegistry`.
2. ETAPA 6 (resposta final do chat) migrada para usar esse registro: tenta OpenRouter primeiro (mais rápido — ~600-900ms medido vs ~2-3s do `InvokeLLM`), cai automaticamente para o Base44 se o provider preferido falhar. Nunca literal-only-OpenRouter-sem-fallback — decisão consciente de manter rede de segurança.
3. O desvio de "Serviço de IA direto" (`AI-SERVICE-DIRECT`, já existente mas nunca validado) foi corrigido (2 bugs: palavras-chave informais faltando; e keywords em `capabilityDetector` vs. condição de trigger) e **movido para o início do pipeline** (ETAPA 0, antes de memória/capacidades) — pedidos de tradução/resumo/transcrição/geração de código agora pulam ~3s de processamento desnecessário.

## Consequências

### Positivas
- Resposta padrão do chat ~2-3x mais rápida na maioria das mensagens (confirmado em produção).
- Caminho para cache de prompt nativo (disponível via OpenRouter/Anthropic/OpenAI, não via `InvokeLLM` do Base44) — não implementado ainda, mas agora arquiteturalmente possível sem nova migração.
- Sistema de tradução/resumo/transcrição/geração de código validado end-to-end pela primeira vez (13 ferramentas Gmail MCP retornadas com sucesso em teste relacionado no mesmo dia).
- Extensível: adicionar um novo provider de IA (visão computacional, transcrição dedicada) segue o mesmo molde — implementar `AIProvider`, registrar.

### Negativas / Trade-offs
- Dependência adicional em disponibilidade do OpenRouter (mitigada pelo fallback automático).
- Bloco fixo de instruções do sistema (~16KB, regras anti-confabulação) continua sendo reenviado em toda mensagem — cache de prompt seria o próximo passo para eliminar esse custo, não implementado nesta sessão.

## Componentes Afetados

- `src/lib/ai-provider-registry/*` (novo)
- `src/lib/reasoning/memoryReasoningPlanner.js` (ETAPA 6 migrada; ETAPA 0 nova para desvio de serviço de IA)
- `src/lib/reasoning/serviceDetector.js` (palavras-chave informais adicionadas: "traduz", "resume", "transcreve")
- `base44/functions/openrouterChat/entry.ts` (já existente, reaproveitada sem alteração)

## Alternativas Rejeitadas

| Alternativa | Motivo da Rejeição |
|---|---|
| Manter só `InvokeLLM`, sem registro de providers | Não resolveria a necessidade explícita do usuário de conectar múltiplas IAs especializadas por capacidade |
| OpenRouter como único provider, sem fallback pro Base44 | Risco de indisponibilidade sem rede de segurança — rejeitado por segurança operacional |
