# ADR-002 — Goal Runtime: Promoção v0.1 → v1.0
**ADR-ID:** ADR-002
**Título:** Goal Runtime: Estratégia de Promoção de v0.1 para v1.0 (EF-24)
**Data:** 2026-07-11
**Status:** Proposed
**DAP de origem:** DAP-02
**Sprint:** SPR-ADR-01

---

## 1. Contexto

### Por que a decisão existe

Goal Runtime existe como v0.1 em `src/lib/goal-runtime-v01/` com 21 cenários de teste certificados. O padrão Engineering First exige 28 cenários + arquivo de tipos separado (`*Types.ts`) para que um módulo seja considerado v1.0 e elegível para integração no produto.

INT-03 (Sprint de integração do Goal Runtime no produto como substituto de `detectGoal()`) depende de um Goal Runtime formalmente certificado como v1.0. A questão é: a promoção ocorre antes ou em paralelo à integração?

### Componentes afetados

- `src/lib/goal-runtime-v01/GoalRuntime.ts` — módulo a ser promovido
- `src/lib/goal-runtime-v01/GoalTypes.ts` — existe, mas tipos podem estar incompletos
- `src/lib/goal-runtime-v01/GoalContract.ts` — contrato existente
- `src/lib/reasoning/goalDetector.js` — componente a ser substituído no produto
- Goal Registry Service (EF-02) — depende de Goal Runtime como dependência upstream
- Goal Scheduler (EF-03) — idem
- Execution Dispatcher (EF-05) — idem
- Goal Execution Queue (EF-04) — idem

### Evidências do código

- `src/lib/goal-runtime-v01/goalRuntimeTests.ts` — 21 cenários (padrão EF: 28)
- `src/lib/goal-runtime-v01/GoalTypes.ts` — arquivo existe (diferente de outros módulos que têm tipos inline)
- `src/lib/reasoning/goalDetector.js` — keyword matching, produz `{ id, label, strategy, type, priority }` — formato diferente de GoalTypes EF
- AUDIT-Sprint0 §2 — confirma 21 cenários, sem `GoalRuntimeTypes.ts` separado dos Types existentes
- NB-02 no FREEZE-CHECKLIST — item não-bloqueante, mas recomendado antes de v2.0

---

## 2. Problema

### Conflito existente

Goal Runtime v0.1 tem 21 cenários. Módulos que dependem dele (Goal Registry: 22, Goal Scheduler: 22, Execution Dispatcher: 24, Goal Execution Queue: 24) têm mais cenários que o módulo fundacional. Esta inversão viola a lógica de certificação: dependentes mais cobertos que a fundação.

Adicionalmente, o objeto Goal produzido por `detectGoal()` no produto (`{ id, label, strategy, type, priority }`) é incompatível com o `Goal` type do EF (`{ id, status, priority, metadata, lifecycle }`). Esta incompatibilidade deve ser resolvida antes de INT-03.

### Por que impede o congelamento

Não bloqueia diretamente o congelamento (NB-02, não BLOQ), mas bloqueia INT-03. Se INT-03 é executada com v0.1, o produto entra em produção com módulo sub-certificado. Risco RA-03 no Risk Register.

---

## 3. Alternativas

### Alternativa A — Promover v0.1 para v1.0 antes de INT-03

**Como funciona:** Sprint dedicada (EF-24) antes de INT-03. Adicionar 7 cenários faltantes (para atingir 28), verificar/completar `GoalRuntimeTypes.ts`, renomear diretório de `goal-runtime-v01/` para `goal-runtime/`, atualizar todas as referências.

**Vantagens:**
- INT-03 usa módulo formalmente certificado v1.0
- Elimina dívida técnica antes da integração
- Módulos dependentes (EF-02, EF-03, EF-04, EF-05) apontam para o canonical correto
- Consistência: fundação mais coberta que dependentes

**Desvantagens:**
- Adiciona um sprint de infra antes de INT-03
- Atrasa a convergência do produto com o pipeline EF

**Impacto:** INT-03 atrasada por 1 sprint (EF-24).

**Risco:** Baixo — promoção é editorial/incremental, não arquitetural.

**Esforço estimado:** 1 sprint (EF-24): 7 cenários + GoalRuntimeTypes.ts + renomeação de diretório + atualização de imports.

---

### Alternativa B — Integrar v0.1 no produto e promover em paralelo

**Como funciona:** INT-03 usa `goal-runtime-v01/` como está (v0.1). Sprint EF-24 acontece em paralelo ou logo após, sem bloquear INT-03.

**Vantagens:**
- Convergência mais rápida
- A funcionalidade de v0.1 é suficiente para os casos de uso de INT-03
- Não bloqueia o roadmap de integração

**Desvantagens:**
- Produto em produção com módulo v0.1 não totalmente certificado
- Dívida técnica acumulada: enquanto v1.0 não chega, v0.1 pode receber correções que divergem da promoção
- Imports de INT-03 referenciam `goal-runtime-v01/` — exige segundo refactor quando v1.0 chegar (renomeação de diretório)

**Impacto:** INT-03 sem atraso. EF-24 como sprint paralela ou posterior.

**Risco:** Médio — produto em produção com módulo abaixo do padrão EF por período indeterminado.

**Esforço estimado:** INT-03 (sem overhead) + EF-24 paralela (1 sprint adicional posteriormente).

---

### Alternativa C — Integrar v0.1 e nunca promover formalmente

**Como funciona:** v0.1 permanece como está. A integração no produto valida funcionalmente. Promoção para v1.0 é descartada — o produto é a validação.

**Vantagens:**
- Zero overhead adicional
- O produto é o teste real

**Desvantagens:**
- Viola o padrão EF de certificação formal
- Cria exceção na arquitetura: único módulo EF sem certificação v1.0
- Dependentes (EF-02, EF-03, EF-04, EF-05) continuam referenciando fundação sub-certificada
- Inconsistência com todos os outros módulos (EF-08 a EF-13 têm 24-28 cenários)

**Impacto:** Cria dívida arquitetural permanente.

**Risco:** Alto — viola padrão EF; cria precedente de módulos sub-certificados.

**Esforço estimado:** Zero para promoção; custo alto em manutenção e inconsistência.

## 7. Recomendação Técnica

**Recomendação: Alternativa A (Promover antes de INT-03)**

Fundamentação:

1. O esforço é pequeno: 7 cenários adicionais + `GoalRuntimeTypes.ts` + renomeação de diretório
2. Evita dupla migração de imports (v0.1 → produto → v1.0)
3. Elimina o risco de produto em produção com módulo sub-certificado (RA-03)
4. Alinha Goal Runtime com o padrão de todos os outros módulos EF (24-28 cenários)
5. Goal Runtime é a fundação de 4 módulos downstream — certificação correta na fundação protege todos eles

**Sequência recomendada:**
```
EF-24 (promoção v0.1 → v1.0, ~1 sprint)
  ↓
INT-03 (integração Goal Runtime v1.0 no produto)
```

*Esta recomendação não constitui aprovação. A decisão final deve ser tomada por humano.*
