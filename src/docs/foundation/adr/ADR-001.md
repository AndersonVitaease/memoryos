# ADR-001 — Intent Layer: Estratégia de Classificação
**ADR-ID:** ADR-001
**Título:** Estratégia de Classificação da Intent Layer (EF-22)
**Data:** 2026-07-11
**Status:** Proposed
**DAP de origem:** DAP-01
**Sprint:** SPR-ADR-01

---

## 1. Contexto

### Por que a decisão existe

A Intent Layer (EF-22) é o primeiro elo entre a UI de chat e o pipeline cognitivo EF. Ela recebe a mensagem bruta do usuário e produz a estrutura de intenção que orienta todo o pipeline downstream: quais entidades consultar, se é uma query de listagem, quais keywords usar para busca.

A implementação atual em `src/lib/memoryPipeline.js:55` (`interpretIntent()`) realiza esta classificação via chamada completa ao LLM (`base44.integrations.Core.InvokeLLM()` com INTENT_SCHEMA). Existe um fallback determinístico por keyword splitting quando a chamada LLM falha.

A arquitetura EF propõe que a Intent Layer seja determinística, eliminando esta chamada LLM. A estratégia de implementação não está definida e é a decisão pendente.

### Componentes afetados

- `src/lib/memoryPipeline.js` — contém `interpretIntent()` que será substituída
- `src/lib/reasoning/memoryReasoningPlanner.js` — orquestra o fluxo que usa o output de interpretIntent
- Intent Layer (EF-22) — módulo a ser implementado
- Context Engine (EF-20) — depende do output da Intent Layer
- Conversation Engine (EF-21) — depende de EF-20

### Evidências do código

- `src/lib/memoryPipeline.js:55` — `interpretIntent()` chama `InvokeLLM` com INTENT_SCHEMA
- `src/lib/memoryPipeline.js:42-53` — INTENT_SCHEMA define: `query_types` (array de enum), `is_list_query` (boolean), `search_keywords` (array de string)
- Fallback em `memoryPipeline.js` — keyword splitting quando LLM falha
- `src/lib/reasoning/memoryReasoningPlanner.js:58` — usa output de `runMemoryPipeline` que inclui intent

---

## 2. Problema

### Conflito existente

Dois produtores de intent coexistem sem definição de canonical:

1. `interpretIntent()` — LLM-based, em produção, afeta respostas reais
2. Intent Layer (EF-22) — não existe, deve substituir o item 1

Enquanto a estratégia de EF-22 não for definida, o módulo não pode ser implementado. Sem EF-22, INT-02 não pode ser executada. Sem INT-02, o pipeline EF permanece desconectado do produto (RC-03 no Risk Register).

### Por que impede o congelamento

BLOQ-05 no ARCHITECTURE-FREEZE-CHECKLIST: o contrato público da Intent Layer deve ser congelado antes de implementação. A estratégia escolhida determina o contrato (determinística retorna confidence; híbrida retorna também o fallback usado; LLM+cache não tem confidence). Congelar o contrato com estratégia errada gera breaking change nos módulos downstream.

## 3. Alternativas

### Alternativa A — Determinística Pura (regras + keyword matching)

**Como funciona:** Tabela de padrões regex + keyword sets mapeiam a mensagem para `query_types`. Exemplo: "mostre todas as tarefas" → `query_types: ["tasks"]`, `is_list_query: true`. Nenhuma chamada externa.

**Vantagens:**
- Latência zero (sem I/O)
- Custo zero (sem créditos LLM)
- Comportamento 100% previsível e testável offline
- Facilita certificação EF (28 cenários determinísticos)

**Desvantagens:**
- Menor cobertura semântica: mensagens incomuns, multilíngues ou ambíguas podem falhar na classificação
- Manutenção manual: novos `query_types` exigem atualização da tabela de regras
- Sem graduação: resultado é binário (classificou / não classificou)

**Impacto:** Substitui completamente `interpretIntent()`. Elimina InvokeLLM #1.

**Risco:** Baixo — fallback do `memoryPipeline.js` já existe e funciona por keyword splitting (prova de que abordagem determinística é viável).

**Esforço estimado:** 1 sprint (implementação de EF-22 + 28 cenários de aceitação).

---

### Alternativa B — Híbrida (determinística com fallback LLM)

**Como funciona:** Classificador determinístico executa primeiro. Se `confidence < threshold` (ex: 0.7), cai para InvokeLLM como fallback. Retorna também `classification_method: "deterministic" | "llm"`.

**Vantagens:**
- Performance no caso comum (sem LLM)
- Qualidade preservada no caso difícil
- Mesma cobertura semântica que hoje
- Transição suave: fallback LLM já existe

**Desvantagens:**
- Latência variável: usuário não sabe se terá 0ms ou 500ms de overhead
- Custo variável: difícil prever consumo de créditos
- Dois caminhos a manter e testar
- Threshold arbitrário sem critério objetivo para ajuste

**Impacto:** Reduz InvokeLLM #1 na maioria dos casos, mas não elimina.

**Risco:** Médio — threshold pode ser mal calibrado; comportamento inconsistente.

**Esforço estimado:** 1.5 sprints (determinístico + integração LLM fallback + calibração de threshold).

---

### Alternativa C — LLM com Cache por Hash

**Como funciona:** Mantém `InvokeLLM` como classificador. Adiciona cache keyed por hash normalizado da mensagem (lowercase + trim + remove punctuation). Hit de cache retorna imediatamente; miss chama LLM e armazena.

**Vantagens:**
- Qualidade LLM preservada em 100% dos casos
- Latência reduzida em mensagens repetidas (cache hit)
- Menor esforço de implementação (adiciona cache ao `interpretIntent()` existente)

**Desvantagens:**
- Não é determinístico: respostas LLM podem variar mesmo para a mesma mensagem
- Cache invalida com mudanças de modelo ou schema
- Custo em novas mensagens (sem cache hit)
- Viola objetivo arquitetural de Intent Layer determinística
- Cache de LLM não é certificável com cenários de aceitação EF padrão

**Impacto:** Melhora latência marginal; não resolve o problema arquitetural.

**Risco:** Médio — não é substituto real da Intent Layer EF; perpetua dependência LLM.

**Esforço estimado:** 0.5 sprints (apenas adiciona cache).

## 7. Recomendação Técnica

**Recomendação: Alternativa A (Determinística Pura)**

Fundamentação:

1. O fallback existente em `memoryPipeline.js` já é determinístico por keyword splitting e funciona em produção — prova direta de viabilidade
2. O output de `interpretIntent()` (INTENT_SCHEMA) é finito e mapeável: `query_types` tem enum de ~8 valores, `is_list_query` é boolean, `search_keywords` são extraíveis com NLP simples
3. Alternativa A é a única que permite certificação EF formal com 28 cenários determinísticos offline
4. Alternativa B perpetua latência variável e custo imprevisível
5. Alternativa C não resolve o problema arquitetural (Intent Layer continua sendo LLM-based)

**Contrato público recomendado para congelamento:**
```typescript
IntentLayer.detect(message: string): IntentResult {
  intent_type: "query" | "command" | "reflection" | "unknown",
  query_types: Array<"tasks" | "decisions" | "documents" | "people" | "topics" | "knowledge" | "general">,
  is_list_query: boolean,
  search_keywords: string[],
  confidence: number // 0.0 - 1.0
}
```

*Esta recomendação não constitui aprovação. A decisão final deve ser tomada por humano.*
