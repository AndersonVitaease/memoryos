# ADR-013 — Microsoft Graph Connector: Capability Executors Pattern

**Status:** Accepted
**RFC Origem:** RFC-006
**Prioridade:** ALTA
**Sprints afetadas:** MS-EXP-01, MS-EXP-02, MS-EXP-03, MS-EXP-04
**Data:** 2026-08-03
**Autor:** MemoryOS Engineering

---

## Contexto

O `MicrosoftGraphConnector` atual expoe 8 capacidades (Outlook Mail, Calendar, OneDrive) num unico `switch` dentro de `execute()`. O usuario pediu cobertura dos 11 servicos do Microsoft 365 (adicionar Contacts, To Do, OneNote, Teams, SharePoint, Excel/Word/PowerPoint Online).

Adicionar 7 servicos ao switch atual produziria um arquivo monolitico de 800+ linhas — padrao rejeitado no passado (dead end: switches insustentaveis, arquitetura monolitica baseada em lista).

---

## Decisao

Adotar o padrao **Capability Executors** (Caminho 2 do RFC-006):

1. O `MicrosoftGraphConnector` torna-se um **shell fino** — mantem apenas token, health, metadata e roteamento `operation → executor`.
2. Cada servico do Microsoft 365 vira um **Capability Executor** isolado em arquivo proprio (`OutlookMailCapability.ts`, `ContactsCapability.ts`, `TeamsCapability.ts`, etc.).
3. Um `MicrosoftCapabilityRegistry` mapeia cada `operation` ao seu executor.
4. Um `MicrosoftGraphHelper` compartilha `graphFetch()`, `ok()`, `fail()` entre todos os executors.

---

## Alternativas Consideradas

### Alternativa A — Estender o switch atual (rejeitada)
- **Pro:** zero arquitetura nova, entrega em horas.
- **Contra:** arquivo monolitico de 800+ linhas, mistura logica de 10 servicos, dificil de manter e testar. Repete o padrao rejeitado no passado.

### Alternativa B — Capability Executors (ACEITA)
- **Pro:** cada servico isolado e testavel, alinha com o padrao JA estabelecido pelos conectores Google (`GmailCapabilityExecutor`, `GoogleDriveCapabilityExecutor`, `GoogleCalendarCapabilityExecutor`), mantem o shell fino.
- **Contra:** mais arquivos para criar agora.
- **Decisao:** alinha o Microsoft com o padrao Google ja estabelecido, ao inves de criar uma estrutura nova.

### Alternativa C — Provider Registry completo estilo WhatsApp (rejeitada)
- **Pro:** simetria arquitetural com o WhatsApp.
- **Contra:** o Microsoft Graph e uma **unica API oficial** — nao ha provedores concorrentes a abstrair. Criar `MicrosoftProviderRegistry` com um unico `GraphProvider` e indirecao sem beneficio. Viola a decisao preferida do projeto: nao inflar arquitetura speculativa.

---

## Justificativa

O padrao de Capability Executors ja e o padrao **vivo e em producao** para os conectores Google (3 executors separados por servico). O Microsoft hoje e a excecao — tudo num switch so. Esta decisao **alinha o Microsoft com o padrao existente**, em vez de introduzir uma estrutura nova.

A arquitetura 5-camadas do WhatsApp foi motivada por **3 provedores concorrentes** (Meta, Evolution, Baileys) — situacao que nao se aplica ao Microsoft Graph (provedor unico). Replicar essa arquitetura seria indirecao sem valor.

---

## Consequencias

- **Positivas:**
  - Cada servico testavel e mantido isoladamente.
  - Adicionar servico novo = 1 arquivo novo + 1 entrada no registry (nunca crescer o shell).
  - Padrao consistente com conectores Google.
  - Shell do conector fica legivel e estavel.

- **Negativas:**
  - Mais arquivos no repositorio (11 executors + 1 helper + 1 registry).
  - Refator inicial necessario para extrair os 8 cases existentes (Fase 0, zero comportamento novo).

- **Neutras:**
  - Escopos OAuth precisam expandir (7 novos) — documentado no RFC-006.
  - Teams/SharePoint exigem tenant corporativo — limitacao da conta Microsoft, nao da arquitetura.

## Implicacoes para Componentes Existentes

| Componente | Impacto | Acao |
|---|---|---|
| `MicrosoftGraphConnector.ts` | Shell fica fino, logica movida para executors | Refator (Fase 0 + 1) |
| `MicrosoftAuthSession.js` | Adiciona 7 escopos no `WORKSPACE_SCOPES` | Edicao aditiva |
| `GoalCapabilityRegistry.ts` | Adiciona mappings para 8 novos prefixos de capability | Edicao aditiva |
| `ConnectorBootstrap.ts` | Nenhuma mudanca — conector ja e registrado | Nenhuma |
| `UCRBridge.ts` (Event Layer) | Nenhuma mudanca — ja envolve qualquer conector | Nenhuma |
| `PipelineObservationBridge.ts` (Observation) | Nenhuma mudanca — ja commita qualquer conector | Nenhuma |

---

## Resumo das 7 Decisoes

1. **Padrao:** Capability Executors (shell fino + executors isolados), nao switch monolitico.
2. **Nao e Provider:** Microsoft Graph e provedor unico — nao replicar arquitetura 5-camadas do WhatsApp.
3. **Espelho do Google:** Alinhar com o padrao JA vivo dos conectores Google.
4. **Extracao primeiro:** Fase 0 move os 8 cases existentes sem mudar comportamento.
5. **Registry centralizado:** `MicrosoftCapabilityRegistry` mapeia operation → executor.
6. **Helper compartilhado:** `MicrosoftGraphHelper` extrai `graphFetch`/`ok`/`fail` reutilizaveis.
7. **Escopos incrementais:** Novos escopos solicitados on-demand, nunca no boot.
