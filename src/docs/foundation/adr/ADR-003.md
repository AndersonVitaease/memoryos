# ADR-003 — Semântica de "Plano" no Produto
**ADR-ID:** ADR-003
**Título:** Unificação da Semântica de "Plano": analytics vs. ExecutionPlan
**Data:** 2026-07-11
**Status:** Proposed
**DAP de origem:** DAP-03
**Sprint:** SPR-ADR-01

---

## 1. Contexto

### Por que a decisão existe

O conceito de "plano" existe em dois lugares do codebase com semânticas incompatíveis:

1. **Produto atual** — `plan` em `runReasoningPlan()` é um objeto de analytics/metadados que registra o que aconteceu durante o processamento
2. **Planning Engine EF-07** — `ExecutionPlan` é um objeto de execução formal e imutável que define o que vai acontecer

Ambos usam o nome `plan`. Quando Planning Engine for integrado (INT-03), o produto terá dois objetos chamados `plan` com semânticas incompatíveis.

### Componentes afetados

- `src/lib/reasoning/memoryReasoningPlanner.js` — cria o `plan` analytics atual
- `src/lib/planning-engine/PlanningEngine.ts` — produz `ExecutionPlan`
- `src/lib/planning-engine/PlanningEngineTypes.ts` — define `ExecutionPlan` type
- `base44.analytics.track()` — chamado com propriedades do `plan` analytics
- Decision Engine (EF-06) — produz input para Planning Engine
- Reflection Engine (EF-08) — avalia resultado contra `ExecutionPlan`

### Evidências do código

- `src/lib/reasoning/memoryReasoningPlanner.js:178-191` — construção do objeto `plan` analytics:
  ```js
  plan = { goal, skills, sourcesCount, capabilities, responseTimeMs }
  ```
- `src/lib/planning-engine/PlanningEngineTypes.ts` — `ExecutionPlan`:
  ```ts
  { id, goalId, steps[], complexity, estimatedMs, risk, status }
  ```
- `memoryReasoningPlanner.js:194-209` — `base44.analytics.track()` usa `plan.goal`, `plan.skills`, `plan.sourcesCount`
- BLOQ-02 no ARCHITECTURE-FREEZE-CHECKLIST — bloqueia congelamento v2.0

---

## 2. Problema

### Conflito existente

O objeto `plan` atual (`{ goal, skills, sourcesCount, capabilities, responseTimeMs }`) é um sumário do que aconteceu — descritivo e retroativo. `ExecutionPlan` (`{ steps[], complexity, estimatedMs, risk }`) é um prescritivo e prospectivo — define o que vai ser executado.

Se INT-03 integra Planning Engine sem resolver esta divergência:
- Código pode usar `plan.goal` (analytics) onde deveria usar `plan.steps[0]` (executável)
- `Reflection Engine` (EF-08) espera `ExecutionPlan` como baseline; se recebe o analytics `plan`, avaliação é incorreta
- `base44.analytics.track()` usa `plan.*` — se `plan` passa a ser `ExecutionPlan`, propriedades não existem → erro silencioso

### Por que impede o congelamento

BLOQ-02 no ARCHITECTURE-FREEZE-CHECKLIST: contratos públicos devem ser definitivos antes do congelamento. `PlanningEngine.plan() → ExecutionPlan` é um contrato do módulo EF certificado. Ele não pode coexistir com um objeto homônimo de semântica diferente no produto.

## 3. Alternativas

### Alternativa A — Renomear objeto analytics para `executionMetrics`

**Como funciona:** Em `memoryReasoningPlanner.js`, renomear `plan` para `executionMetrics`. `base44.analytics.track()` passa a usar `executionMetrics.*`. Planning Engine assume o nome `plan` com semântica de `ExecutionPlan`.

**Exemplo:**
```js
// Antes
const plan = { goal, skills, sourcesCount, capabilities, responseTimeMs }
base44.analytics.track({ properties: { goal: plan.goal, ... } })

// Depois
const executionMetrics = { goal, skills, sourcesCount, capabilities, responseTimeMs }
base44.analytics.track({ properties: { goal: executionMetrics.goal, ... } })
```

**Vantagens:**
- Semântica clara: `plan` = ExecutionPlan EF; `executionMetrics` = analytics retroativo
- Sem perda de dados de analytics
- Mudança mínima: rename em um arquivo + atualização do analytics.track
- Libera o nome `plan` para uso exclusivo do Planning Engine

**Desvantagens:**
- Mudança de nomenclatura em `memoryReasoningPlanner.js` — requer atenção durante INT-03
- `executionMetrics` é um nome mais longo e pode parecer redundante com `responseTimeMs` que já está dentro

**Impacto:** Pequeno — mudança localizada em um arquivo.

**Risco:** Baixo — rename é mecânico; sem mudança de comportamento.

**Esforço estimado:** < 1 hora (editorial). Pode ser feito como pré-requisito de INT-03.

---

### Alternativa B — Dois objetos coexistindo com nomes distintos

**Como funciona:** Mantém `plan` analytics como está. Planning Engine retorna objeto com nome diferente, ex: `executionPlan` (camelCase). O tipo `ExecutionPlan` já usa PascalCase — o objeto em runtime seria `executionPlan`.

**Exemplo:**
```js
const plan = { goal, skills, ... }          // analytics — inalterado
const executionPlan = PlanningEngine.plan() // EF — novo
```

**Vantagens:**
- Zero breaking change no objeto `plan` atual
- Analytics inalterados
- Nenhuma refatoração em `memoryReasoningPlanner.js`

**Desvantagens:**
- Dois conceitos de "plano" no mesmo arquivo: `plan` e `executionPlan`
- Desenvolvedores futuros podem confundir os dois
- Reflection Engine (EF-08) recebe `executionPlan` mas documentação pode referenciar `plan`
- Não resolve a ambiguidade de nomenclatura a longo prazo

**Impacto:** Nenhum imediato; risco de confusão crescente.

**Risco:** Médio — confusão semântica acumulada.

**Esforço estimado:** Zero (nenhuma mudança).

---

### Alternativa C — Substituição total: remover `plan` analytics

**Como funciona:** O objeto `plan` analytics é removido. Analytics extrai dados do `ExecutionPlan` quando necessário. Propriedades do `plan` analytics mapeadas para campos do `ExecutionPlan`.

**Mapeamento:**
```
plan.goal          → executionPlan.goalId
plan.skills        → executionPlan.metadata.skills
plan.sourcesCount  → executionPlan.metadata.sourcesCount
plan.capabilities  → executionPlan.steps[].type
plan.responseTimeMs → executionPlan.actualDurationMs (campo novo)
```

**Vantagens:**
- Único objeto de plano no sistema
- Sem ambiguidade
- `ExecutionPlan` como fonte única de verdade para analytics e execução

**Desvantagens:**
- `ExecutionPlan` precisaria de campos `metadata.*` adicionais para preservar os analytics
- Breaking change em `base44.analytics.track()` — propriedades mudam
- Altera o contrato de `ExecutionPlan` (EF-07) adicionando campos não previstos
- Mistura responsabilidades: `ExecutionPlan` passa a carregar dados de analytics além de dados de execução

**Impacto:** Médio — altera contrato de EF-07 e analytics.

**Risco:** Médio — chance de perda de dados de analytics durante migração.

**Esforço estimado:** 1 sprint (refatoração + migração de analytics + atualização de EF-07).

## 7. Recomendação Técnica

**Recomendação: Alternativa A (Renomear objeto analytics para `executionMetrics`)**

Fundamentação:

1. Esforço mínimo: rename em um arquivo + uma linha de analytics
2. Libera o nome `plan` para uso exclusivo e semanticamente correto do Planning Engine
3. Sem breaking change em `ExecutionPlan` (EF-07 permanece inalterado)
4. Alternativa B perpetua ambiguidade; Alternativa C adiciona responsabilidades ao EF-07
5. A renomeação pode ser feita como pré-requisito editorial de INT-03, sem sprint dedicada

**Ação mínima para desbloquear BLOQ-02:**
1. Renomear `plan` → `executionMetrics` em `memoryReasoningPlanner.js`
2. Atualizar `base44.analytics.track()` na mesma linha
3. Congelar contrato: `PlanningEngine.plan(decision) → ExecutionPlan`

*Esta recomendação não constitui aprovação. A decisão final deve ser tomada por humano.*
