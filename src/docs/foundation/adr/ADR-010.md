# ADR-010 — Unificação da Pipeline de Busca Web (Serper como motor único)

**Status:** Implemented
**Data:** 2026-07-30
**RFC:** N/A (decisão emergiu de investigação de performance, não de RFC prévio)
**Autor:** Sessão de engenharia assistida (Claude) + Anderson Vitaease

---

## Contexto

O sistema tinha **dois mecanismos independentes de busca web**, cada um com sua própria lógica de decisão de quando disparar:

1. `SearchEngine` (`src/lib/search-engine/`) — motor formal com providers registrados, decidia via lista fixa de palavras-chave em `WebSearchProvider.ts` (posteriormente substituído por `SerperSearchProvider.ts`).
2. `capabilityDetector.js` → `capabilityExecutor.js` — sistema de capacidades mais antigo, com detecção por palavra-chave **e** uma checagem semântica via LLM (`semanticWebSearchCheck`), que executava a busca via `base44.integrations.Core.InvokeLLM({ add_context_from_internet: true })`.

O caminho (2) foi medido em produção levando **26.000–43.000ms** por chamada, sem timeout algum. Isso era a causa raiz do maior gargalo de latência do sistema.

## Decisão

1. Substituímos o backend de busca do `WebSearchProvider` por uma integração com a API da **Serper** (busca pura, sem LLM), via nova function `serperSearch` + `SerperSearchProvider.ts`.
2. `capabilityExecutor.js` (`executeWebSearch`) foi **redirecionado** para usar o mesmo `SearchEngine`/Serper, em vez do `InvokeLLM` com grounding de internet — eliminando a duplicação de backend.
3. Adicionada coordenação: se `capabilityDetector` (ETAPA 4) já resolveu a busca com sucesso, `SearchEngine` (ETAPA 5.2) é pulado — evita busca duplicada na mesma mensagem.
4. `SearchEngine.search()` foi alterado de `Promise.all` (espera todos os providers) para resolver assim que **qualquer** provider atinge confiança suficiente — evita que um provider lento (ex: `mcp_registry`, com timeout de 15s) segure a resposta mesmo com um resultado bom já disponível.
5. Adicionado timeout de 8s em `semanticWebSearchCheck` (a checagem via LLM que decide se aciona a busca) — antes sem limite, contribuía para os timeouts globais de 90s observados.

## Consequências

### Positivas
- Latência de busca: **26.000–43.000ms → 1.500–2.900ms** (medido em produção, múltiplas execuções).
- Detecção semântica de intenção ("verifique se X", sem palavra-chave óbvia) preservada — só a execução mudou de backend.
- Travas anti-confabulação (IA-084, IA-086) estendidas para reconhecer resultado de ambos os caminhos (não só o antigo).

### Negativas / Trade-offs
- Busca por palavra-chave pura (Serper) não faz desambiguação de termo vago usando contexto da conversa, como o `InvokeLLM` fazia dentro do próprio prompt (ex: "servidor" sozinho virando "servidor MCP Mercado Livre"). Aceito conscientemente em troca da velocidade.
- Dependência de um provedor externo pago (Serper) em vez de usar só a IA já contratada — custo adicional, ainda que baixo em volume esperado.

## Componentes Afetados

- `base44/functions/serperSearch/entry.ts` (novo)
- `src/lib/search-engine/SerperSearchProvider.ts` (novo, substitui `WebSearchProvider.ts`)
- `src/lib/search-engine/SearchEngine.ts` (lógica de resolução alterada)
- `src/lib/search-engine/registerProviders.ts` (registro trocado)
- `src/lib/reasoning/capabilityExecutor.js` (`executeWebSearch` redirecionado)
- `src/lib/reasoning/capabilityDetector.js` (timeout adicionado a `semanticWebSearchCheck`; condição de skip ajustada para considerar `hasMemoryForTopic`)
- `src/lib/reasoning/memoryReasoningPlanner.js` (coordenação ETAPA 4/5.2; travas IA-084/086 estendidas)

## Alternativas Rejeitadas

| Alternativa | Motivo da Rejeição |
|---|---|
| Manter `InvokeLLM` com grounding, só adicionar timeout | Resolve o timeout, não resolve a lentidão inerente (LLM fazendo leitura+síntese é sempre mais lento que busca pura) |
| Desligar `capabilityDetector`'s `semanticWebSearchCheck` inteiramente | Perderia a detecção de casos ambíguos sem palavra-chave; optou-se por redirecionar o backend em vez de remover a inteligência de detecção |
