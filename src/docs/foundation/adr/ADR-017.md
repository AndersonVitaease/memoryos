# ADR-017 — Adaptive Process Engine

**Status:** Proposed
**Date:** 2026-08-05
**RFC Origem:** RFC-010
**EPIC:** EPIC-020
**Prioridade:** ALTA
**Sprints afetadas:** AP-01, AP-02, AP-03, AP-04, AP-05
**Arquivo:** `src/docs/foundation/adr/ADR-017.md`

---

## Contexto

O MemoryOS possui uma cadeia de execução consolidada (ADR-015) onde cada
**capability** é uma ação relativamente atômica (`gmail.send`,
`drive.search`, `github.search`, `issueAirTicket`). O Planner resolve um
goal em um plano de steps, o Runtime despacha, o Connector traduz a API.

O **Deep Research** não é uma ação atômica. É um processo cognitivo composto
que planeja, executa diversas capabilities, avalia resultados, detecta
lacunas, pesquisa novamente, aplica critério próprio de parada e sintetiza
um relatório. Possui 3 propriedades estruturais que o diferenciam de uma
capability comum:

1. **Auto-orquestração de capabilities** com decisão dinâmica sobre quais
   chamar.
2. **Loop reflexivo com critério de parada não-trivial** (gap-detection →
   re-plan → executar até satisfazer qualidade, não contador fixo).
3. **Estratégia de parada própria** baseada em suficiência de evidência.

A mesma forma interna aparecerá em futuros processos (Deep Planning, Root
Cause Analysis, Opportunity Discovery, Strategy Builder, Multi-Agent
Investigation, Compliance, Negotiation, Optimization). Tratar cada um como
capability comum criaria N arquivos com a mesma forma interna e nenhum nome
coletivo — débito arquitetural a evitar.

Esta ADR documenta como acomodar essa nova categoria sem distorcer a
arquitetura pública e sem criar bifurcação invisível no Runtime.

---

## Decisão

Adotar abordagem **híbrida**: externamente o Deep Research é apenas uma
capability (`deepResearch()`); internamente é implementado por um
**Adaptive Process** — nova categoria arquitetural interna, invisível na
arquitetura pública.

### Decisões arquiteturais específicas

1. **Arquitetura pública inalterada** — 4 elementos (Planner → Capability
   Registry → Dispatcher → Connector). Adaptive Process é detalhe de
   implementação. O modelo mental do desenvolvedor não muda.

2. **Metadata `composite` no `ConnectorMetadata`** — campo opcional
   `capabilityComposite?: Record<string, boolean>` em `ConnectorTypes.ts`,
   espelhando `capabilityReversibility` (EI-01). O Runtime lê o flag e
   aplica política de execução composta (sub-budget, correlation tree,
   timeout estendido, auth propagation). Sem o flag, o hibridismo cria
   bifurcação invisível; com o flag, a bifurcação é declarada e barata.

3. **`AdaptiveProcessConnector`** — connector shell (id
   `"adaptive-process"`) com capability `deepResearch` (`composite: true`,
   reversibility `safe`). Seu `execute("deepResearch")` delega ao
   `DeepResearchProcess`. Registrado no `ConnectorBootstrap`; mapeado no
   `GoalCapabilityRegistry` como qualquer connector.

4. **Reentrada pela cadeia completa** — o `DeepResearchProcess` invoca
   sub-capabilities via `runtime.processCapability({ ...,
   parentExecutionId })`. Cada sub-cap passa por Intelligence + Safety +
   Dispatch (bypass impossível por construção, herda ADR-015). O Runtime
   detecta aninhamento via `parentExecutionId` e aplica sub-budget próprio,
   correlação em árvore (`SystemEvent.parentId`), propagação de auth
   context, circuit breaker isolado.

5. **Nome "Adaptive Process"** — a propriedade ontológica real é adaptação
   ao plano, não cognição. "Cognitive" limitaria a processos LLM-driven;
   "Adaptive" sobrevive a Compliance/Negotiation/Optimization não-cognitivos
   que têm as mesmas 3 propriedades estruturais.

6. **Sem `AdaptiveProcessRegistry` (YAGNI)** — a interface `AdaptiveProcess`
   nasce agora; o connector detém diretamente a instância de
   `DeepResearchProcess`. O registry surge quando o 2º processo for
   concreto (Deep Planning, RCA, etc.). Criar agora é abstração para 1.

7. **Localização em `src/lib/execution-intelligence/adaptive-process/`** —
   dentro do diretório vivo da cadeia ADR-015. Não em `src/runtime/` nem
   `src/sdk/` (árvores paralelas mortas). Não nos 2 Capability Registries
   paralelos (`src/lib/marketplace/`, `src/lib/capabilities/registry/`).

## Alternativas consideradas

### Alternativa A — Deep Research como Goal (rejeitada)
Forçar o Planner a iterar reflexivamente. Rejeitada: o Planner é
declarativo e estático por SRP; iteração reflexiva não é sua
responsabilidade. Criaria um "segundo Planner", fragmentando o mental model.

### Alternativa B — Deep Research como Capability comum, sem flag (rejeitada)
Registrar `deepResearch` sem distinguir de `gmail.send`. Rejeitada: cria
bifurcação invisível — o Runtime aplica política atômica a um processo
composto. Bug silencioso: timeout mata o processo aos 30s; `SystemEvent`
registra 1 evento e as 40 sub-chamadas ficam órfãs; auth context não
propaga para sub-chamadas.

### Alternativa C — Adaptive Process como categoria pública (rejeitada)
Adicionar 5º elemento visível na arquitetura. Rejeitada: aumenta o modelo
mental sem necessidade. O hibridismo (externo capability, interno processo)
preserva a simplicidade externa e a abstração reutilizável interna.

### Alternativa D — AdaptiveProcessRegistry desde o início (rejeitada)
Criar o registry com a primeira instância. Rejeitada por YAGNI: com 1
processo não há abstração a extrair. A interface nasce agora; o registry
surge naturalmente com o 2º.

### Alternativa E — Nome "Cognitive Process" (rejeitado)
Limita a LLM-driven. "Adaptive" captura a propriedade real (replaneja
baseado em resultados) sem viés de mecanismo.

## Consequências

### Positivas
- Deep Research roteável como qualquer capability (zero aprendizado novo).
- Runtime aplica política correta a processos compostos sem novo conceito
  público.
- Interface `AdaptiveProcess` reutilizável por futuros processos (Deep
  Planning, RCA, Strategy Builder, etc.) — a abstração nasce pronta.
- Árvore de correlação preservada (sub-caps como filhas em `SystemEvent`).
- Arquitetura pública permanece 4 elementos.

### Negativas
- Runtime ganha um branch de política. Mitigada: branch é puro wiring de
  política em helper isolado; `processCapability` permanece puro wiring
  (ADR-015 invariant #3 preservado).
- `AdaptiveProcessConnector` chama de volta o Runtime (referência circular
  conceitual). Mitigada: referência injetada via contexto/setter no wiring
  (index.ts), mesmo padrão lazy de `getExecutionRuntime()`.

### Neutras
- `ConnectorMetadata` ganha mais um campo opcional. `ConnectorBootstrap`
  não o valida. Connectors que não declaram `composite` continuam idênticos.

---

## Invariants arquiteturais (não-negociáveis)

1. **Arquitetura pública inalterada** — 4 elementos. Adaptive Process é
   detalhe de implementação.
2. **Bifurcação declarada, não invisível** — o flag `composite` diz a
   verdade ao Runtime.
3. **Reentrada pela cadeia completa** — sub-caps passam por
   `processCapability` (Intelligence + Safety + Dispatch). Bypass
   impossível por construção (herda ADR-015).
4. **YAGNI no registry** — sem `AdaptiveProcessRegistry` até o 2º processo.
5. **Aditivo apenas** — nada apagado; caminho antigo intocado até AP-05.

---

## Reuso de padrão já vivo

Esta ADR não inventa padrão novo. Reusa:
- "Shell fino + implementação interna isolada" — vivo em
  `MicrosoftGraphConnector` + 11 executors (ADR-013), `WhatsAppConnector`
  + 3 providers, `ExecutionIntelligence` + 7 módulos (ADR-015).
- Campo opcional no `ConnectorMetadata` espelhando `capabilityReversibility`
  (EI-01) — mesmo arquivo, mesmo padrão, mesmo zero-impacto-em-bootstrap.
- `getExecutionRuntime()` lazy wiring (ADR-015 EI-04) — para injetar a
  referência do Runtime no `AdaptiveProcessConnector` sem circular init.

## Verificação de não-quebra

- `ExecutionRuntime.processCapability` (ADR-015) ganha um branch de
  política (AP-04), não reescrita. O caminho de capabilities não-composite
  é idêntico.
- Os 11 executors do Microsoft Graph (ADR-013), os 3 providers do WhatsApp,
  os 11 executors do Base44 (RFC-009), o Execution Intelligence completo
  (EI-01..EI-07) — todos intocados.
- `UCRBridge` (Event Layer), `PipelineObservationBridge` (Observation
  Layer), `ConnectorBootstrap`, `GoalCapabilityRegistry` — intocados até
  AP-03 (registro aditivo) e AP-05 (sinais aditivos).
- Até AP-05, `deepResearch` não tem sinais no `GoalRegistry` → Planner
  nunca o roteia → nenhum caller vivo o invoca. O `AdaptiveProcessConnector`
  (AP-03) é inerte até AP-05.
- Cada sprint deploya sozinha; build verde entre fases.

## Fases de implementação

| Sprint | Foco | Risco |
|---|---|---|
| AP-01 | `composite` metadata flag | Zero |
| AP-02 | AdaptiveProcess interface + DeepResearchProcess | Zero |
| AP-03 | AdaptiveProcessConnector + mapping (inerte) | Baixo |

evolução real do Runtime. AP-05 abre ao usuário. Cada sprint é reversível.
