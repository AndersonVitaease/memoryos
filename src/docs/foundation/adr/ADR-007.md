# ADR-007 — Reasoning Engine: Módulo Separado ou Responsabilidade Distribuída
**ADR-ID:** ADR-007
**Título:** Reasoning Engine: Módulo EF Independente vs. Responsabilidade Distribuída
**Data:** 2026-07-11
**Status:** Proposed
**DAP de origem:** DAP-07
**Sprint:** SPR-ADR-01

---

## 1. Contexto

### Por que a decisão existe

A arquitetura oficial lista "Reasoning Engine" como um dos módulos do pipeline cognitivo. No codebase atual:

- `src/lib/reasoning/` existe como diretório com 11 arquivos JavaScript (goalDetector, contextBuilder, capabilityOrchestrator, memorySynthesizer, memoryReasoningPlanner, capabilityExecutor, capabilityDetector, serviceDetector, macrFormatter, macrFormatterV4, capabilities)
- Este diretório é uma coleção de utilitários do produto, não um módulo EF formal (sem Types EF, sem testes padrão EF, sem index EF)
- As responsabilidades de "raciocínio" estão distribuídas por: Context Engine (EF-20), Planning Engine (EF-07), Reflection Engine (EF-08), Conversation Engine (EF-21)

A questão é: deve existir um módulo `reasoning-engine/` separado com responsabilidade própria, ou a responsabilidade de "raciocínio" é intrinsecamente distribuída pelos módulos acima?

### Componentes afetados

- `src/lib/reasoning/` — 11 arquivos de utilitários do produto
- Context Engine (EF-20) — cobre recuperação e montagem de contexto
- Planning Engine (EF-07) — cobre planejamento de execução
- Reflection Engine (EF-08) — cobre avaliação de resultado
- Conversation Engine (EF-21) — cobre orquestração do fluxo
- TARGET-ARCHITECTURE.md — pipeline oficial a ser atualizado com a decisão
- ARCHITECTURE-FREEZE-CHECKLIST.md — BLOQ-01 depende desta decisão

### Evidências do código

- `src/lib/reasoning/memoryReasoningPlanner.js` — é o "reasoning" de mais alto nível: orquestra todo o pipeline de raciocínio
- `src/lib/reasoning/goalDetector.js` — será incorporado no Goal Runtime (EF-24)
- `src/lib/reasoning/contextBuilder.js` — será incorporado no Context Engine (EF-20)
- `src/lib/reasoning/capabilityOrchestrator.js` — será substituído pelo Capability Runtime (EF-15)
- `src/lib/reasoning/memorySynthesizer.js` — será incorporado na Reflection Engine (EF-08)
- Após as migrações INT-02 a INT-07: `src/lib/reasoning/` terá apenas `memoryReasoningPlanner.js` → que se tornará Conversation Engine
- BLOQ-01 no ARCHITECTURE-FREEZE-CHECKLIST — bloqueia congelamento v2.0
- ARCHITECTURE-VALIDATION-REPORT §2.18 — status 🟡

---

## 2. Problema

### Conflito existente

Após as migrações INT-02 a INT-07 completadas, o diretório `src/lib/reasoning/` terá seus componentes distribuídos pelos módulos EF correspondentes. Sobra apenas `memoryReasoningPlanner.js` → que se tornará Conversation Engine (EF-21).

Um "Reasoning Engine" separado, nesse cenário, precisaria de uma responsabilidade que:
- Não seja coberta por Context Engine (monta contexto)
- Não seja coberta por Planning Engine (cria plano)
- Não seja coberta por Reflection Engine (avalia resultado)
- Não seja coberta por Conversation Engine (orquestra o fluxo)
- Não seja coberta por Goal Runtime (gerencia Goals)
- Não seja coberta por Decision Engine (decide capabilities)

Não existe evidência no código de uma responsabilidade de raciocínio que cumpra esse critério.

### Por que impede o congelamento

BLOQ-01: o pipeline oficial inclui "Reasoning Engine" entre Reflection Engine e LLM Gateway. Se ele for removido do pipeline, TARGET-ARCHITECTURE.md deve ser atualizado. O pipeline congelado não pode ter um módulo indefinido.

## 3. Alternativas

### Alternativa A — Remover Reasoning Engine do pipeline (responsabilidade distribuída)

**Como funciona:** "Reasoning Engine" não existe como módulo EF separado. A responsabilidade de "raciocínio" é o resultado da composição de:
- Intent Layer: classifica intenção
- Goal Runtime: cria Goal com semântica
- Decision Engine: decide capabilities
- Planning Engine: cria plano de execução
- Context Engine: monta contexto cognitivo
- Reflection Engine: avalia resultado
- Conversation Engine: orquestra tudo

**Vantagens:**
- Sem sobreposição de responsabilidade
- Pipeline mais enxuto (sem módulo de responsabilidade vaga)
- Consistente com evidências do código: após migrações, `reasoning/` fica vazio exceto pelo Conversation Engine
- Remove ambiguidade do pipeline oficial

**Desvantagens:**
- Altera TARGET-ARCHITECTURE.md (remove um módulo do pipeline)
- "Reasoning Engine" some da arquitetura oficial — pode parecer regressão
- Requer atualização de todos os documentos que mencionam Reasoning Engine

**Impacto:** Editorial — nenhum código é afetado. TARGET-ARCHITECTURE.md atualizado.

**Risco:** Baixo — mudança de documentação.

**Esforço estimado:** < 1 hora (atualização de documentação).

---

### Alternativa B — Manter Reasoning Engine como módulo EF separado com meta-cognição

**Como funciona:** Reasoning Engine (EF-25+) tem responsabilidade de "meta-cognição": integra os resultados de múltiplos módulos e decide se o raciocínio foi suficiente antes de chamar o LLM. Exemplo: "dado o contexto, o plano, e a decisão — é necessário refinar antes de prosseguir?"

**Posição no pipeline:** entre Planning Engine e LLM Gateway (após decisão e plano, antes da chamada LLM).

**Vantagens:**
- Preserva arquitetura oficial
- Adiciona camada de qualidade: valida raciocínio antes do LLM
- Responsabilidade diferenciada: meta-cognição (avaliar se o raciocínio está completo)

**Desvantagens:**
- Alta sobreposição com Reflection Engine (que avalia resultado) e Planning Engine (que valida plano)
- Meta-cognição é difícil de testar formalmente (quando o raciocínio é "suficiente"?)
- Sem evidência no código de que esta responsabilidade é necessária
- Adiciona latência no path crítico (outra avaliação antes do LLM)
- Pode tornar-se um módulo vazio em prática

**Impacto:** Novo módulo a implementar (EF-25 ou renumerado).

**Risco:** Alto — responsabilidade vaga é difícil de certificar.

**Esforço estimado:** 2-3 sprints (definição de responsabilidade + implementação + 28 cenários).

---

### Alternativa C — Renomear diretório `reasoning/` para módulo EF formal sem mudar responsabilidades

**Como funciona:** `src/lib/reasoning/` é elevado a módulo EF `reasoning-engine/` com o que já existe, sem reorganizar os componentes individuais para seus módulos corretos. É uma formalização do existente.

**Vantagens:**
- Zero esforço de implementação
- Preserva estrutura existente

**Desvantagens:**
- NÃO resolve o problema: os componentes de `reasoning/` têm responsabilidades que pertencem a outros módulos EF (goalDetector → Goal Runtime; contextBuilder → Context Engine; etc.)
- Formaliza uma violação de SRP em vez de corrigi-la
- Após INT-02 a INT-07, o módulo ficaria vazio — seria removido depois

**Impacto:** Cosmético — não resolve o conflito arquitetural.

**Risco:** Alto — perpetua SRP violations.

**Esforço estimado:** Zero, mas cria problema maior.

## 7. Recomendação Técnica

**Recomendação: Alternativa A (Remover Reasoning Engine do pipeline)**

Fundamentação:

1. Evidência do código: após migrações INT-02 a INT-07, `src/lib/reasoning/` fica vazio. O diretório `reasoning/` é um artefato do estágio atual (pré-EF), não uma responsabilidade arquitetural permanente
2. Não existe responsabilidade de "raciocínio" que não seja coberta por um módulo EF já certificado
3. Alternativa B cria um módulo com responsabilidade vaga ("meta-cognição") sem evidência de necessidade — viola o princípio de "não criar módulos sem evidência no código"
4. Resolver BLOQ-01 requer apenas atualizar TARGET-ARCHITECTURE.md para remover "Reasoning Engine" do pipeline — ação editorial

**Impacto editorial de Alternativa A:**
- TARGET-ARCHITECTURE.md §3: remover "Reasoning Engine" do pipeline final
- Adicionar nota: "A responsabilidade de raciocínio é distribuída por Context Engine, Planning Engine, Decision Engine e Reflection Engine"

*Esta recomendação não constitui aprovação. A decisão final deve ser tomada por humano.*
